🛡️ Error Boundary

مدیریت خطاهای runtime با global error handler و دایرکتیو zen-error

errorSignal onError reportError zen-error directive fallback UI graceful-degradation

۱. اکشن که خطا می‌دهد — Event Delegation آن را می‌گیرد

وقتی یک action خطا می‌دهد، لایه‌ی Event Delegation آن را catch می‌کند و جلوی خرابی کل فریم‌ورک را می‌گیرد. دکمه‌ی زیر عمداً خطا می‌دهد. کل فریم‌ورک پایدار می‌ماند.

✅ خطا در اکشن catch شد. فریم‌ورک همچنان کار می‌کند — روی دکمه‌های دیگر کلیک کنید! 
Zen.action('throwError', () => {
  throw new Error('خطای عمدی از داخل اکشن!');
});
// event delegation این خطا را catch می‌کند — فریم‌ورک پایدار می‌ماند.

۲. خطای Expression — zen-text با expression نامعتبر

وقتی expression داخل zen-text (یا zen-bind، zen-if، zen-html) خطا دهد، خود دایرکتیو آن را catch می‌کند، reportError را صدا می‌زند و مقدار خالی نمایش می‌دهد. کلیک کنید تا یک expression نامعتبر فعال شود.

نام کاربر:
⚠️ $userData برابر null است. Expression $userData.name خطا می‌دهد اما توسط zen-text catch شده و مقدار خالی نمایش داده می‌شود. 
<span zen-text="$userData.name"></span>
// اگر $userData = null باشد، expression خطا می‌دهد.
// zen-text خطا را catch می‌کند، reportError() صدا می‌زند،
// و textContent = '' تنظیم می‌کند.

۳. zen-error Directive — Fallback سفارشی

با دایرکتیو zen-error می‌توان یک section را wrap کرد. اگر Expression داخلش خطا دهد، fallback UI نمایش داده می‌شود. در این دمو، processErrorBoundary به‌صورت دستی فراخوانی می‌شود (این دایرکتیو به‌صورت خودکار در runtime walker ثبت نشده است). 

<div zen-error>
  <span zen-text="$profile.name"></span>
  <template zen-fallback>
    <div>⚠️ خطا در نمایش پروفایل</div>
  </template>
</div>

// در JavaScript:
processErrorBoundary(el, processChildren, disposes);
// fallback در el.__zenithFallback__ ذخیره می‌شود.
// هنگام خطا، showFallback(el, fallback) را صدا می‌زنیم.

۴. خطا در zen-for — بقیه‌ی آیتم‌ها همچنان رندر می‌شوند

اگر یک آیتم در zen-for داده‌ی نامعتبر داشته باشد، فقط همان آیتم خطا می‌دهد. بقیه‌ی آیتم‌ها بدون مشکل رندر می‌شوند. این graceful degradation است.

# (داده نامعتبر)
💡 در این لیست ۵ آیتم وجود دارد. آیتم‌های #۲ و #۴ داده‌ی user برابر null دارند. Expression $u.user.name برای آن‌ها خطا می‌دهد اما بقیه‌ی آیتم‌ها (#۱، #۳، #۵) به‌طور معمولی رندر می‌شوند. 
const users = [
  { id: 1, user: { name: 'علی' } },
  { id: 2, user: null },  // ← خطا در $u.user.name
  { id: 3, user: { name: 'زهرا' } },
  { id: 4, user: null },  // ← خطا در $u.user.name
  { id: 5, user: { name: 'محمد' } },
];
// zen-for هر آیتم را جداگانه رندر می‌کند.
// خطا در یک آیتم، بقیه را تحت تاثیر قرار نمی‌دهد.

۵. onError — لاگ سراسری خطاها

با onError(callback) می‌توان همه‌ی خطاهای runtime را به یک handler سراسری فراخوانی کرد. این برای ارسال خطاها به سرویس‌های monitoring (مثل Sentry) مفید است. هر خطا که در این دمو رخ دهد، در لاگ زیر ظاهر می‌شود.

۶. Recovery — clearError

با clearError()، errorSignal به null برمی‌گردد. این کار به UI اجازه می‌دهد دوباره محتوای اصلی را نمایش دهد (اگر data اصلاح شده باشد). 

import { clearError, errorSignal } from '@zenith/error-boundary';
clearError();
console.log(errorSignal.get());  // null

خلاصه

@zenith/error-boundary دو لایه‌ی مدیریت خطا فراهم می‌کند: ۱) Global: errorSignal، onError، reportError — در همه‌ی دایرکتیوها یکپارچه شده. ۲) Local: دایرکتیو zen-error برای wrap کردن section ها با fallback UI. خطاهای runtime هیچ‌وقت کل اپ را خراب نمی‌کنند — graceful degradation.
