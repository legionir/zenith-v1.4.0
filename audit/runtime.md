# گزارش حسابرسی پکیج `runtime`
**نسخه:** v1.3.0 | **بسته:** `@zenith/runtime`

---

## ۱. خلاصه پکیج

پکیج `runtime` هسته‌ی اجرایی فریم‌ورک Zenith است trách任运行および管理框架的生命周期。このパッケージは Zen オブジェクトを提供し、これがフレームワークの主要なインターフェースとなります。

主要な責務：
- DOMの初期化とZenithフレームワークの起動 (`Zen.start`)
- フレームワークのシャットダウンとリソースのクリーンアップ (`Zen.stop`)
- アクション登録と管理 (`Zen.action`)
- プラグインシステム (`Zen.use`)
- ローカルステート管理（`signal`, `effect`, `computed`, `batch`の再エクスポート）
- ルーティング統合 (`Zen.navigate`, `Zen.route`)
- デバッグツール統合 (`Zen.devtools`)
- エラーバウンダリ統合 (`@zenith/error-boundary`から)
- コンポーネントローディング (`@zenith/components`から)
- スケジューリング (`@zenith/scheduler`から)
- データフェッチング (`@zenith/data`から)
- セキュリティユーティリティ (`@zenith/security`から)

## ۳. باگ‌ها و مشکلات

### BUG-RUNT-01: イベントデリゲーションのクリーンアップに関する潜在的な問題
- **schwere Wassermittel:**
- **'emplacement:** `src/index.ts` - `Zen.stop` メソッド、行281-288
- **説明:** `Zen.stop` は `(root as any).__zenithDelegationTeardown` を消費し、そのあと削除します。ただし、この teardown 関数が複数回呼び出される場合（例えば、誤ってまたはHMRシナリオで）、二重のクリーンアップが発生しようとする可能性があります。現在の実装はこの関数を一度だけ消費するため、後続の呼び出しは `undefined` を取得し、早期に終了します。これは実際的には問題ではありませんが、明示的に二重呼び出しを防ぐ設計が望ましいです。
- **방향 수정:** テーダウン関数を null に設定した後に、二重呼び出しに対する明示的なチェックを追加するか、またはテーダウン関数自身が二重呼び出しに対して冪等であることを確認してください（ほとんどの実装ではすでにそうであるべきです）。

### BUG-RUNT-02: グローバル DevTools フラグへの依存
- **schwere Wassermittel:**
- **Miejsce:** `src/index.ts` - `isDevMode()` 関数、行76-81
- **説明:** `isDevMode()` 関数は、`window.__ZENITH_DEV__` などのグローバルフラグに依存しています。これはほとんどの場合機能しますが、フレームワークが複数のフレームまたはワーカー（例：サービスワーカー、iframe）の中で使用される場合、これらのフラグが期待通りに伝播しない可能性があります。これにより、異なるコンテキスト間での開発モードの検出の不一致が生じます。
- **방향 수정:** より堅牢な開発モード検出メカニズムを実装することを検討してください。たとえば、ビルド時に定義されるもの（`import.meta.env.DEV`のようなViteのメカニズム、またはバンドル時の定義）または複数のコンテキストを通じて一貫性を保つ方法を調べてください。

### BUG-RUNT-03: Plugin システムのインストール状態の競合条件
- **schwere Wassermittel:**
- **Miejsce:** `src/index.ts` - `Zen.use` メソッド、行391-411
- **説明:** `Zen.use` メソッドはプラグインのインストール状態をチェックし（行396）、その後インストールを試みます（行403）。ただし、このチェックと設定の間に競合状態が発生する可能性があり、同じプラグインの複数の同時呼び出しが複数回のインストール試行を引き起こす可能性があります。現在の実装では、2番目以降の試行では警告が発生し（行398）、これは無害ですが、理想的には、最初のチェック後に設定が行われるまでの間に、他の同時呼び出しが同じことを試みることを防ぐべきです。
- **방향 수정:** インストール状態のチェックと設定をアトミック操作にするため、ミューテックスまたは同様のメカニズムを使用することを検討してください。あるいは、ダブルチェックロックパターンを実装することもできます（ただし、JavaScriptではこれを正しく行うのは難しいです）。

### BUG-RUNT-04: FOUC 방지 스타일 주입 가능성 실패
- **schwere Wassermittel:**
- **Miejsce:** `src/index.ts` - `__injectCloakStyle()` メソッド、行479-491
- **説明:** `__injectCloakStyle` メソッドは、同じ ID を持つスタイル要素が既に存在する場合、スタイルを再挿入しません（行483-484）。ただし、このスタイル要素がページから削除されたが、 DOM から参照が保持されている場合（例えば、以前の Zen.start 呼び出し中に保存された参照がある場合）、メソッドはまだ false を返し、スタイルを再挿入しません。これにより、FOUC 防止スタイルが欠如している状況が発生する可能性があります。
- **방향 수정:** スタイル要素の存在だけでなく、それが実際にドキュメントのヘッドに接続されているかどうかもチェックしてください（`style.parentNode === document.head` のようなチェック）。

### BUG-RUNT-05: イベントデリゲーションの初期化における潜在的なリーク
- **schwere Wassermittel:**
- **Miejsce:** `src/index.ts` - `Zen.start` メソッド、行223-227
- **説明:** `Zen.start` は、`initEventDelegation` からのティーダウン関数を `(root as any).__zenithDelegationTeardown` に保存します。ただし、このルート要素がその後 `Zen.stop` を呼び出さずに削除または置き換えられた場合、この参照はガベージコレクションによって収集されません（ルートが他の場所で参照されている場合を除く）。これは長時間実行されるアプリケーションでは問題にはなりませんが、単一ページアプリケーション（SPA）では頻繁にルート要素が置き換えられるため、時間とともに参照が蓄積されます。
- **방향 수정:** ルート要素が削除されたことを検出するメカニズムを実装することを検討してください（たとえば、ミューテーションオブザーバーを使用するか、またはルート要素が接続解除されたときに発生するイベントをリッスンする）、または、`Zen.stop` を明示的に呼び出さなくても参照をクリアする方法を調べてください。

### BUG-RUNT-06: グローバル HMR ロード関数のリーク可能性

### BUG-RUNT-07: デバッグツールフックのインストールにおける潜在的な競合条件
