# DEC-024: `charts` و `icons` — community/اختیاری تا بازخورد مصرف‌کنندگان

- وضعیت: پذیرفته‌شده • ۲۰۲۶-۱۰-۱۰ • issueهای مرتبط: #175 (main)، #161–#170 (P2 اپیک‌ها)، SPEC §۴.۹/§۴.۱۰

## زمینه

`NEW-PACKAGES-SPEC.md` ریسک ۵: `charts` (L2، ≤۲۰KB، وابسته shared+schema) و `icons` (L2، ≤۱KB هسته) در SPEC «اختیاری» (مرحلهٔ ۹ نقشه) علامت‌گذاری شده‌اند و ممکن است بهتر باشد پکیج جامعه (community) باشند؛ تصمیم نهایی موکول به بازخورد کاربران شده است.

## گزینه‌ها

- **الف) رسمی از همان اول (publish under `@zenith/`)** — تعهد نگهداری/امنیت/SLO روی دو پکیج پرریسک UI-محور (چارت کتابخانه‌ای سنگین؛ آیکون داده‌محور) که هستهٔ فریمورک نیستند. ❌
- **ب) community/اختیاری: repo جدا یا پوشهٔ `community/` با namespace `@zenith-community/*`، بدون SLA رسمی، با درِ ورود به رسمی‌شدن (حداقل ۲ نسخه استفادهٔ واقعی + feedback issue پر)**. ✅ (پیش‌فرض SPEC)
- **ج) حذف کامل** — اکوسیستم‌ساز را نمی‌شود حذف کرد؛ فقط وضعیت رسمی‌بودن تصمیم است. ❌

## تصمیم و دلیل

گزینهٔ ب — پیش‌فرض SPEC بدون قید فنی خلاف، و §4.3 دستورالعمل (پذیرش پیش‌فرض مشخصات). مبنای صنعتی: الگوی Vue (vueuse vs chart.js اکوسیستم)، Svelte (sveteks)، Angular components: مواد داده‌محور/کتابخانه‌محور خارج از core bundle نگهداری می‌شوند تا بودجهٔ حجم و چرخهٔ release هسته آلوده نشود. رسمی‌شدن بعداً فقط «جابه‌جایی namespace + تحویل SLA» است، نه بازنویسی API — چون از همان اول با قرارداد #117/#171 ساخته می‌شوند.

## پیامدها

- ردیف ۹ نقشهٔ SPEC: «اختیاری — community (DEC-024)»؛ هیچ issue P0/P1 به آن‌ها گره نمی‌خورد.
- اگر مصرف‌کننده‌ای خواست، RFC رسمی‌شدن با شاخص‌های بالا باز است؛ ساختار tests/CI community جوری می‌چرخد که ارتقا به رسمی هزینه‌بر نباشد.
- `icons` در صورت رسمی‌شدن باید subset-tree-shakeable بماند (`≤ 1 KB` هسته در size-limit قفل است).
